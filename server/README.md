# SmartSite AI — API server

Express + Prisma + better-auth backend for the SmartSite AI frontend. It was
rebuilt from `src/assets/schema.prisma` and the endpoints the frontend calls.

## Quick start (local, no accounts needed)

```bash
cd server
npm install
npm run dev:local
```

That derives a SQLite schema from `schema.prisma`, creates `dev.db`, and starts
the API on port 4000. Sign-up and sign-in work immediately. Generating a website
additionally needs `GEMINI_API_KEY` in `.env` — until it is set, generation
fails cleanly and refunds the credits it charged.

`prisma/dev.prisma` is generated by `scripts/make-dev-schema.mjs` — never edit it
by hand. `prisma/schema.prisma` (PostgreSQL) stays the single source of truth.

## Setup (PostgreSQL / production)

1. **Install dependencies**

   ```bash
   cd server
   npm install
   ```

2. **Create `.env`**

   ```bash
   cp .env.example .env
   ```

   Fill in these four values:

   | Variable | Where to get it |
   | --- | --- |
   | `DATABASE_URL` | Neon → your project → Connection string (pooled) |
   | `DIRECT_URL` | Neon → the same project → unpooled connection string |
   | `BETTER_AUTH_SECRET` | `openssl rand -base64 32` |
   | `GEMINI_API_KEY` | https://aistudio.google.com/apikey — free tier, no card |

3. **Create the database tables**

   ```bash
   npx prisma migrate dev --name init
   ```

4. **Run it**

   ```bash
   npm run dev
   ```

   The API listens on **port 4000**, and the frontend `.env` already points
   `VITE_BASEURL` at it. Port 3000 is deliberately avoided — another project on
   this machine (a Next.js app) permanently holds it, and pointing the frontend
   there is what produced the original "API not working" 404s.

## Endpoints

Auth is handled by better-auth at `/api/auth/*` (email + password).

| Method | Route | Purpose |
| --- | --- | --- |
| GET | `/api/user/credits` | Remaining credits |
| GET | `/api/user/projects` | The signed-in user's projects |
| POST | `/api/user/projects` | Start a generation → `{ projectId }` |
| GET | `/api/user/projects/:id` | One project, with versions + conversation |
| GET | `/api/user/publish-toggle/:id` | Publish / unpublish |
| POST | `/api/user/purchase-credits` | Credit purchase (no provider wired yet — returns 503) |
| PUT | `/api/project/save/:id` | Save edited code as a new version |
| DELETE | `/api/project/:id` | Delete a project |
| GET | `/api/project/preview/:id` | Code + versions for preview |
| GET | `/api/project/published` | Community feed (public) |
| GET | `/api/project/published/:id` | Published project's code (public) |
| GET | `/api/project/rollback/:id/:versionId` | Restore a version |
| POST | `/api/project/revision/:id` | AI revision of an existing site |

Generation and revision cost 5 credits each; new accounts start with 50. If a
generation fails, its credits are refunded automatically.

**Generation is asynchronous.** `POST /api/user/projects` returns a project id
immediately and fills in `current_code` in the background — the frontend polls
every 10 seconds until it appears. Revisions are synchronous and can take a
couple of minutes.

## Deploying

The frontend deploys to Vercel; this server needs a host that runs a long-lived
Node process (Render, Railway, Fly). Vercel's serverless functions time out well
before a generation finishes.

Set the same environment variables on the host, plus:

- `CLIENT_URL` — the deployed frontend origin, e.g. `https://your-app.vercel.app`
- `SERVER_URL` — this API's public URL
- `NODE_ENV=production` — required, so session cookies are sent with
  `SameSite=None; Secure` and survive the cross-origin hop from Vercel

Build and start commands: `npm run build` then `npm start`. Run
`npx prisma migrate deploy` against the production database once.
